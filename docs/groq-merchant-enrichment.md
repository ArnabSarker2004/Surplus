# Local merchant cleanup and optional Groq suggestions

Updated September 26, 2026. Cleanup results apply automatically, with separate provenance from bank evidence and user corrections. Toronto/TMU recognition now uses one shared catalogue in TypeScript and Python. This supplements the [merchant evidence workflow](transaction-enrichment.md), without activating paid Plaid Enrich.

## Setup

1. Create a free account at [Groq Console](https://console.groq.com). Create an API key and check your organization's model access and limits.
2. Save `GROQ_API_KEY=your-key` in the root server `.env`. Do not use a `VITE_` prefix or send the key in chat. `GROQ_MODEL=openai/gpt-oss-20b` is the default; it is listed in the current free-tier limits. The Llama model IDs in the original plan are currently listed as enterprise offerings, so they are not assumed free. No automatic model or paid-tier fallback occurs.
3. Run `npm run db:migrate` if setting up another database, then restart `npm run dev` so Express and Python receive the key.
4. Open **Transactions → Cleanup settings**, or **Money outlook → Transaction cleanup settings** at the bottom of any tab. Enable **Use Groq for unfamiliar merchants** once for a live workspace. Existing opt-outs are respected. Cleanup starts when the view opens and after bank sync; remaining external batches continue while the view is open, within the service's limits.
5. Usable results appear automatically in the list and forecasts. Select a merchant name or category to open the inline editor. **Remember this for the same merchant** saves a rule for future imports and other uncorrected matches. **Details & split purchase** contains receipt splits and original bank evidence. No per-transaction acceptance is required. Corrections survive future bank sync.

Without a key or opt-in, cleanup remains local. The public demo makes no enrichment requests; a signed-in sample workspace can exercise local cleanup but never sends data to Groq.

## Pipeline and safeguards

`shared/data/toronto-merchants.json` supplies the version, bounded regional descriptor patterns, payment wrappers and Groq glossary to both TypeScript and Python. Local matches run against the original descriptor before store numbers and region evidence are removed. Recognized wrappers include `ONLINE PURCHASE`, `TELEPHONE ORDER` and `RECURRING PYMNT` with compact bank dates. Python also keeps the existing Starbucks, Tim Hortons, Netflix and Spotify aliases. Brand digits, acronyms and punctuation such as `H&M` remain intact. Arbitrary substrings such as `Starbucks Consulting`, `PRESTO Pizza` and `TTC Treasury Services` do not become transit/retail matches.

PRESTO's documented `PRES/` confirmation format and observed ten-character references resolve locally to **PRESTO → TTC and PRESTO**, without sending their references to Groq. PRESTO fare/load and recognized station descriptors, TTC, GO Transit, UP Express, MiWay and named GTA transit agencies also resolve locally. A bare `PRES`, `GO`, `UP` or location name is insufficient; no route, operator or student fare is inferred from a PRESTO debit reference. See [PRESTO's statement format](https://www.prestocard.ca/en/help-centre/help-by-topic/faq?type=accountManagement) and [Metrolinx's transit list](https://www.metrolinx.com/en/discover/more-ways-to-pay-presto-introduces-debit-taps-on-transit).

TMU and legacy Ryerson names are recognized with explicit food, printing, tuition and residence qualifiers. A **OneCard top-up**, generic **TMU** or **TMU Financial Services** can have a clean name with no inferred purchase category. The Campus Store gets the broad Shopping estimate unless the descriptor specifies textbooks/printing. [OneCard supports several kinds of campus purchases](https://www.torontomu.ca/onecard/using-your-onecard/pay-for-products-and-services/); it is not automatically tuition. Grocery store descriptors include Metro with a store number, Food Basics, FreshCo, Farm Boy, No Frills and [Foody World](https://www.foodyworld.ca/). Bike Share Toronto, Green P and fuel retailers can be identified without forcing them into the app's transit-fare category.

Groq receives the same fixed regional glossary for unfamiliar descriptors. This supplies domain knowledge, not claims about the user's school, address, commute or receipt. The model may identify a merchant while returning a null category. No user profile is added to the external payload. Known local matches, including ones with an ambiguous purpose, do not consume Groq requests. Synthetic positive and lookalike fixtures are shared by the TypeScript and Python tests.

`shared/merchants.ts` also expands Canadian `SDM` + store-number descriptors into **Shoppers Drug Mart** immediately, including existing records. A store descriptor ending in a Canadian region is required; an isolated acronym or `SDM Consulting` does not qualify. [Ontario's pharmacy listing](https://news.ontario.ca/en/backgrounder/58491/ontario-expands-covid-19-testing-to-pharmacies) identifies store 1382 in Scarborough. A low-confidence, otherwise uncategorized purchase receives the broad Shopping estimate; a specific strong bank category or user correction stays intact. The rule does not infer prescription or grocery receipt items.

Eligible purchase descriptions proceed to Groq when the user has opted in. Meaningful strong Plaid names remain authoritative, but abbreviated names and missing/weak categories can be considered. A category result conflicting with a strong merchant identity is discarded. Rules, user corrections, transfers and recognizable personal-account descriptors are skipped. The request contains only cleaned descriptors and short batch indices: no separate transaction dates, amounts, account IDs, balances, profile or bank credentials. Descriptor text itself can reveal shopping activity; this is disclosed beside the checkbox. Input text is treated as untrusted data, and no tools/web search are enabled.

Normal synchronous chat requests group **up to 20 descriptors**, rather than using Groq's paid asynchronous Batch API. One group is attempted per pass, at most twice a minute and 60 times per day for this Python process. This process-local cap resets on restart and is not a billing guarantee. Actual organization limits can be lower. HTTP 429 honors `Retry-After` without blocking sleep or automatic retry; failures preserve local results and never roll back bank sync. A subsequent pass handles remaining entries. Output must contain exactly the expected IDs, safe merchant strings and allowed Surplus categories; invalid/truncated batches are discarded atomically.

These are **automatic estimates**, not verified identities. Resolved names enter the display and model grouping with `local`/`groq` provenance and `LOCAL_RULE`/`AI_ESTIMATE` confidence. Weak uncategorized purchases receive automatic category changes, marked `categoryOrigin: enrichment`; deterministic local matches can also replace older enrichment estimates. Meaningful bank categories, strong category evidence, splits, deposits, transfers and user edits are preserved. Originals remain in the bank fields, and automatic changes never set `userCorrected` or `merchantOverride`. Remembered corrections for local merchants use a stable name key, so different PRESTO references share the correction; old provider-based rule keys remain accepted on import. Recurrence is inferred from transaction history, not a single LLM subscription claim. The app never infers legal parent companies or receipt line items from a descriptor alone.

## Storage and mapping

| Requested concept                | Existing Surplus field                                                                        |
| -------------------------------- | --------------------------------------------------------------------------------------------- |
| Original `raw_name`              | Immutable transaction `description`                                                           |
| Suggested `clean_merchant`       | `enrichment.merchant`, with `enrichment.cleaned` for deterministic cleanup                    |
| Suggested category               | `enrichment.category`, validated against Surplus's category list                              |
| Automatically applied category   | `category` with `categoryOrigin: enrichment`, applied consistently to stored/imported history |
| User-corrected merchant/category | Existing `merchantOverride` and `category`, through authenticated correction routes           |

Migration `004_merchant_enrichment.sql` creates a per-user cache with forced RLS. Cache keys hash the exact raw descriptor, source, cleanup version (`merchant-cleanup-3`), external-processing preference and model. Results are not shared across users. At most 2,000 entries are retained; successful suggestions, local-only results and externally ineligible descriptors last 90 days, and completed external unknown matches last one day. Unattempted eligible descriptors stay queued for the next pass, subject to the provider cooldown; repeated clicks do not postpone them with a new cache lifetime. First-time lookups precede expired misses. Generic processor-only labels and recognizable private descriptors cannot consume repeated external requests. A transient outage preserves older useful suggestions. Corrections remain authoritative even after cache reuse. Changing source or opting out during a request prevents its results being applied. Clear-data and disconnect remove the cache; raw descriptions remain in the original transaction records until those records are deleted.

Manual enrichment releases the PostgreSQL workspace lock while calling Python and rechecks current state before applying. The existing sync operation serializes imports; its enrichment call is bounded to eight seconds and does not block successful bank data if Python/Groq is unavailable. A deployed, multi-worker version should move enrichment to a durable queue and shared rate limiter.

## Provider references and privacy

[Supported models](https://console.groq.com/docs/models), [rate limits](https://console.groq.com/docs/rate-limits), [JSON output modes](https://console.groq.com/docs/structured-outputs), [Batch API](https://console.groq.com/docs/batch), and [data controls](https://console.groq.com/docs/your-data) were reviewed September 21, 2026; output modes and limits were rechecked September 25. The default model uses strict JSON Schema output. The explicitly supported strict models are GPT OSS 20B/120B and Qwen 3.8 27B; a configured custom model uses JSON object mode. All output is still validated locally for exact batch identity, safe strings and supported categories, including null merchant/category pairs. Both numeric and HTTP-date `Retry-After` values are honored. Groq offers zero-data-retention controls; review your organization's settings. The app does not change the provider's retention settings or enable a paid plan.

Forecasting remains local. Only this separately authorized enrichment endpoint makes an external AI request. No provider response, descriptor, token or key is logged by this feature.
